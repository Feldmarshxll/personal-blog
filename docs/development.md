# Устройство и обслуживание

## Поток сборки

`content/` → валидация Python → `.build/docs/` → Zensical → `.build/site/`.

`validation.py` проверяет типы, даты, идентификаторы и границы файловых путей. `wishlists.py` отвечает за формат списков. `content.py` загружает Markdown и применяет правила публикации. `catalog.py` выводит URL, рубрики, теги и связи серий. `markup.py` формирует HTML каталогов, экранируя строки YAML. `generate.py` объединяет результат. `check.py` разбирает готовые ссылки и якоря без сетевых запросов. `preview.py` предоставляет локальный HTTP-сервер.

Генератор сначала проверяет все источники, затем готовит новый каталог `.build/docs-next/` и заменяет `.build/docs/`. При ошибке в данных предыдущие подготовленные страницы сохраняются. Выходные пути фиксированы и проверяются с разрешением символических ссылок. Рукописные материалы не перезаписываются.

Все итоговые адреса проверяются на совпадения до записи файлов. `index` зарезервирован для страницы раздела и недопустим как slug статьи или проекта, идентификатор серии, рубрики или вишлиста. Авторские ресурсы не могут перезаписывать одноимённые файлы темы.

## Zensical

Используется Zensical 0.0.59. Собственная оболочка в `theme/overrides/` не зависит от Material for MkDocs. Нужные функции блога генерируются перед сборкой: ожидать поддержки blog-плагина не требуется.

Шаблоны используют MiniJinja и стандартный контекст `page`/`config`. `main.html` — общий каркас, `home.html` — главная, `article.html` — статья, `redirect.html` — старые URL. Стили и скрипты находятся в `theme/assets/` и копируются в публикуемые ресурсы.

Перед сборкой создаётся `.build/zensical.yml`: технические настройки берутся из `zensical.toml`, а `site_name`, `site_description` и `extra.site` — из `content/site.yml`. Zensical читает этот временный конфиг; имя и подпись едины на всех страницах, включая 404. YAML поддерживается самим Zensical и не требует установки MkDocs. Для сборки используйте `python -m tools.site_builder build`.

При изменении адреса сайта согласованно обновите `project.site_url` и `project.extra.base_path` в `zensical.toml`. Второе поле содержит URL-путь с завершающим `/`. Генератор проверяет их совпадение. `project.docs_dir` и `project.site_dir` сохраняйте как `.build/docs` и `.build/site`.

Локальный `serve` автоматически пересобирает изменения в `content/`, `theme/` и `zensical.toml`. После изменения Python-модулей остановите сервер и запустите его заново, чтобы загрузить обновлённый код.

## Анимация и доступность

Анимация чёрной дыры — декоративная Canvas-композиция. SVG служит запасным вариантом. Учитываются `prefers-reduced-motion`, видимость вкладки и нахождение первого экрана в области просмотра. Кнопка позволяет управлять паузой. Контент и ссылки доступны без анимации и JavaScript.

Вишлисты генерируются в HTML полностью; JavaScript только фильтрует готовые карточки. Меню и ссылки поддерживают клавиатуру. Фильтры скрыты, пока не выполнена инициализация JavaScript.

## Зависимости и чистота

Прямые зависимости перечислены в `requirements/runtime.in`, полный проверенный набор — в `requirements/lock.txt`. Установка выполняется из lock-файла. Для обновления используйте отдельную ветку и чистое виртуальное окружение, установите выбранные версии из обновлённого runtime.in, получите новый `pip freeze`, затем повторите тесты, сборку, проверку ссылок и браузерную проверку.

В Git попадают только исходники, тесты, документация и конфигурация. `.venv/`, `.build/`, `.cache/`, `__pycache__/`, отчёты и локальные настройки игнорируются. Сборка `gh-pages` — отдельный результат публикации, а не исходная ветка.

## Публикация

Workflow проверяет изменения с правом чтения репозитория. Отдельная задача публикации получает `contents: write` только после успешных проверок и только для push в основную ветку. Публикуется исключительно `.build/site`; история ветки `gh-pages` сохраняется. Настройки Pages продолжают указывать на `gh-pages` и корневой каталог.
